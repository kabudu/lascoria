# Attachments in Lascoria

Status: R14 is partially implemented. Images (PNG, JPEG, GIF, WebP) can be added to a session's next task from 17 October, and MP4/QuickTime videos and UTF-8 text files from 19 October. PDFs, audio, archives and office documents are refused with an explanation because the pinned Muse has no input path for them. Native platform acceptance remains open.

## Current behaviour

The workspace inspector can insert a bounded repository file excerpt into the task draft. The composer submits text, a typed Muse skill, or text with images (see [Images](#images-implemented-17-october)). A path in a prompt is not proof that file bytes were attached.

The pinned official SDK 1.4.10 (schema unchanged from 1.4.9) declares these native paths. Declarations establish the integration shape, not successful native/provider acceptance:

| Content | Native path | Lascoria requirement |
| --- | --- | --- |
| Repository files | Text with `@relative/path`; a structured mention part is rejected | Keep workspace scope visible; distinguish a reference from an included excerpt or uploaded bytes. |
| Images | `image` turn part with media type and base64 bytes | Stage privately, validate format/dimensions/size and submit through the normal explicit Send action. |
| Video | Chunked `media/upload` with session-owned upload receipt, then `video` input | Separate upload/retry/cancellation semantics; expose only after native/model compatibility and limits are proved. |
| PDF, audio, archives or arbitrary binary files | No general file input part in the pinned schema | Do not pretend these are supported by sending a filename or routing them through the video API. Prove a native supported path before enabling each format. |

Primary references: [turn input parts](https://meta-models.github.io/muse-code-sdk/next/generated/msp/types/turninputpart/), [media upload](https://meta-models.github.io/muse-code-sdk/next/generated/msp/methods/media-upload/). The website's next documentation can differ from the pinned SDK; installed types and real native trials on the pinned release determine shipped behaviour. Attachments on answers to Muse questions are reserved/rejected in the pinned schema and must not be advertised.

## Images (implemented 17 October)

**Experience.** One **Add image** control sits under the composer text. Choosing, pasting into the composer or dropping onto it stages images for that session only; nothing is sent until the user starts a task. A compact strip shows each image with a thumbnail (for images added in this window), name, size and dimensions, preparing progress, a per-item error with Retry, and Remove. Waiting images survive reloads and appear in every window of the session. Send waits while an image is preparing or when more than four are waiting. Images are never sent with steering; the strip says so while a task runs. The transcript marks a user message that carried images ("1 image attached"). Help describes the limits.

**Boundary.** The supervisor owns staging under `<state>/attachments/<session>/`, created private (no links, user-only) and written only by these owner-authenticated operations: `attachment/begin` (open session only, announced size), `attachment/append` (ordered base64 chunks of at most 44 KiB, so the 64 KiB control limit is unchanged; an identical retried chunk is accepted, a different one refused), `attachment/finish` (complete size, SHA-256 and content check), `attachment/discard` and `attachment/list`. The type comes from the file header, never the name or declared MIME type, and dimensions come from the PNG, GIF, WebP or JPEG header. Limits: 5 MB per image, 6 MB and four images per task, eight waiting per session, 64 MB in total, 8192 pixels per side and 40 megapixels. The total counts each image's announced size from the moment `attachment/begin` admits it, across all sessions, and admission is serialised, so concurrent or interleaved uploads cannot exceed it before their bytes arrive; the count is derived from the staged manifests, so it survives restarts and is freed by discard, send or expiry. Unfinished uploads in any session expire after ten minutes, checked whenever an upload begins. The composer applies the same 5 MB limit before reading, previewing or hashing a file, using built-in limits until the supervisor reports its own, so a large file is refused before it is loaded into the window's memory. Retry reuses the same upload identity: an upload whose last reply was lost resumes from the bytes already received, or is found already finished, instead of leaving a second copy. There is no frontend file-read command: bytes come from the browser's own file, paste or drop objects.

**Sending.** `turn.attachments` lists staged IDs in order. The supervisor resolves them for that session only and passes verified file paths to the session worker, which re-checks each SHA-256 and sends official `image` input parts after the task text. The command journal keeps IDs only, never bytes. After Muse acknowledges the task, which keeps the bytes in its own durable log, the staged copies are deleted; a retry with the same request returns the original command and sends nothing again. Archiving or removing a session deletes its waiting images. Images live outside the journal, so backups and exports do not include unsent images.

**Evidence.** Rust tests cover base64, header parsing for all four formats, malformed and oversized images, a PDF named `.png`, chunk order and retries, cross-session refusal and bounds. The real-Muse test (`test/attachments.test.js`, Muse 1.4.10 with a controlled loopback model) proves the image bytes reach the model request, the journal holds no bytes, Muse records image metadata on the user message, the staged copy is removed after sending and a retry sends nothing, and that unknown, cross-session, steering and archived-session cases are refused. The Rust-backed UI test (`test/ui/images.spec.ts`) covers choosing, an unsupported file, paste, reload persistence, remove, sending, the transcript marker, accessibility and narrow layout. Review fixes, 18 October: Rust tests reserve announced bytes across interleaved sessions and under 16 concurrent begins (both failed against the previous byte-file accounting), and free reservations on discard and expiry; `test/ui/images-recovery.spec.ts` refuses an oversized image with no upload call while the limits read is held and after it fails, and loses the `finish` and a middle `append` reply after commit, retries and reloads, leaving exactly the two intended images and no orphan staging.

**Open.** Native picker, paste and drag-and-drop on macOS, Windows and Linux (the window now disables Tauri's own file-drop handling so the composer receives HTML drops; that needs native confirmation); behaviour with real provider models, including models without image input; R11 memory and CPU measurements for large images; video, PDFs and other files.

## Videos and text files (implemented 19 October)

**Experience.** The composer control is now **Attach file**; choosing, pasting or dropping images, videos and text files stages them in the same strip, with a kind badge, size, progress, Retry and Remove. Files Muse cannot read (PDF, audio, archives, office documents, other image or video formats) are refused before any byte is read, with the reason. Help lists the limits.

**Probe of the pinned Muse 1.4.10 (19 October, macOS, echo provider).** `media/upload` accepted 4 KiB to 600 MiB uploads in 4 MiB chunks (about 9 ms per MiB) and accepted bytes that were not a video at all; it refused any type other than `video/mp4` or `video/quicktime`. A `video` turn part was accepted and an upload receipt could be used by more than one task. Muse keeps uploaded videos in the session's own store (`input-assets/video`) for the life of the session. With a model provider (the loopback model in `test/attachments.test.js`), Muse then uploads the video to the provider's own file storage through the OpenAI-style Files API (`purpose=user_data`, `expires_after` 2,592,000 seconds, that is 30 days) before the model request; the strip and Help say so whenever a video is waiting. These results set Lascoria's own checks and limits below.

**Boundary.** `attachment/begin` takes a declared `kind` (`image`, `video` or `text`, default `image` for older clients), so the right limit applies before any byte arrives; finish confirms it by content and refuses a mismatch. Videos must start with an ISO base media `ftyp` box (`qt  ` brand means QuickTime, otherwise MP4); text files must be UTF-8 with no NUL bytes. Finish now streams the checksum instead of reading the file into memory. Limits: one video per task, up to 100 MB (it also bounds the copy Muse keeps); text files up to 256 KB each, four and 512 KB per task; still eight waiting per session, and the shared storage reservation is now 256 MB. A video's upload receipt (a UUIDv7) is minted once at begin.

**Sending.** On Send the supervisor hands each video to Muse before dispatching the task: one bounded worker call per 4 MiB chunk, read by the worker from the verified private file (the first call re-checks the whole file's SHA-256, streaming), with a command identity derived from the receipt and chunk number, so a resent task replays chunks Muse already holds instead of storing them twice. The task then carries a `video` part naming the receipt. A text file is re-checked and added after the task text as `<attached_file name=".." bytes="..">` text; the transcript shows the user's own words followed by "Attached: name". The journal keeps attachment IDs only. Staged copies are removed once Muse accepts the task, as for images.

**Evidence.** Rust tests cover MP4 and QuickTime detection, a fake video, text and binary detection, per-kind limits, a retried begin that changes kind, per-task counts and a stable upload receipt; the reservation tests now use 100 MB videos against the 256 MB cap. The real-Muse test (`test/attachments.test.js`) sends a text file with one task through the loopback model and checks the text reaches the model while the journal and what the user sees keep only the name; it sends a video with another and checks Muse uploads it to the provider's file storage, with no video bytes in the journal and the staged copy gone. The loopback model cannot complete a video task, so a full video answer is not proven. The Rust-backed UI test covers attaching a text file next to an image, refusing a PDF and the transcript marker.

**Open.** Whether a real provider model receives and understands the video (the loopback model records the request but cannot judge it), native pick/paste/drop on all three operating systems, and R11 measurements for 100 MB uploads, which pass through the 64 KiB control channel in about 3,100 chunks and are held once in the window's memory while being read.

## Proposed composer experience

Use one small **Add attachment** control beside the composer. Dragging files over the workspace reveals a clear drop target at the composer; pasting an image adds it to the same draft. Selecting or dropping only stages locally. It never interrupts the active task or immediately sends a prompt/upload.

A compact strip above the text shows image thumbnails and file chips with name, type/size, status and an accessible remove action. Selecting a chip opens a preview with a keyboard-accessible close action. A long strip collapses excess items behind a count; it does not open another permanent floating panel. The exact message and attachment order remain visible before Send. Running tasks keep their activity visible while attachments wait in the draft; immediate steering requires a distinct supported action and native validation.

Make states clear: preparing, ready, sending, sent and needs attention. A bad or oversized file explains the limit beside that file. Retry or remove one item without discarding the prompt or other attachments. Unsupported types are rejected with an explanation. An interrupted/unknown send keeps the original request identity and attachment references; recovery must not submit duplicate model/tool work.

## Ownership and bounds

Attachments belong to a session draft, not the selected canvas node or a global clipboard history. Persist references and content fingerprints with the draft, with the same conflict/revision checks as text. Recover after normal close/reopen; explain unavailable/moved inputs. Pending input added by one session must never leak into another.

Keep staged bytes in app-private storage with explicit per-file, total draft, decoded image and retained-storage limits. Verify content signatures, actual file size and decoded dimensions; do not trust filenames or MIME declarations. Never execute attached content or silently follow links outside the selected scope. Treat document/image text as untrusted task data, not permission to run commands.

The normal control request is limited to 64 KiB. Do not raise that global limit or put base64 in the general command journal to make attachments fit. Add a narrow, bounded native staging boundary returning opaque session-owned IDs; stream bounded content through the SDK worker only on explicit send. No arbitrary frontend filesystem read command. Account/provider destination and any conversion must be visible before transmission; no hidden external conversion service.

Define safe cleanup with R5, resource/decode limits with R11, and staging/path/IPC/retention checks with R12. Record native format/model restrictions accurately in the UI. R14 acceptance requires actual image/file workflows on all supported operating systems, recovery, accessibility and privacy validation before completion.
