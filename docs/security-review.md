# Security review (R12)

Started 17 October 2026 against `codex/release-foundations-windows` at `5603378` plus the uncommitted R5/R17/D3 increment. This is the R12 threat model and findings register. It is an evidence-based source review in progress, not a completed audit. Scoped adversarial runtime checks are recorded below; fuzzing and independent review remain open, and a passing scanner or test suite does not close this gate.

## Deployment assumptions

- Lascoria is a single-user desktop application. The Rust supervisor, Node SDK workers, Muse hosts and test commands run as the signed-in operating-system user.
- Other local users and remote network attackers are out of trust. Processes of the same user are not uniformly trusted: repository code (build scripts, test runners, Git hooks, package scripts) and model-directed tools run as the same user but must not gain Lascoria's control authority.
- Muse owns model execution and its native permission prompts. Lascoria must never grant, imply or automate a Muse approval from model output, peer messages or provider confidence.

## Trust boundaries and current controls

1. **WebView to Tauri commands.** Strict CSP (`default-src 'self'`, no remote scripts, `object-src`/`frame-src 'none'`, images limited to `self` and `data:`). No `dangerouslySetInnerHTML`, `eval` or remote content in the React tree; transcripts render as text. The bridge forwards only an allowlisted operation set and caps requests at 64 KiB. Native choosers return only bounded absolute UTF-8 paths; the supervisor revalidates every path before use. Desktop notifications go through two Rust commands with bounded, single-line text; the notification plugin's own IPC commands are not granted to the WebView. Browser hand-off accepts only `https://auth.meta.com/oauth/device/` URLs and avoids shell parsing on every OS.
2. **Local IPC (Unix socket / named pipe).** Unix peers must share the server's UID; Windows pipes have a random 256-bit name, a current-user/SYSTEM DACL and server-SID verification before the client sends the token. Every request carries the token and protocol version. Frames are line-limited to 64 KiB; connection and work admission are bounded (16 connections, 16 queued calls, 16 tasks, 4 per session lane).
3. **Supervisor to Node workers and Muse hosts.** Workers are spawned without a shell, with bounded stdio. Command records are journalled with `synchronous=FULL` before dispatch, uncertain outcomes become `outcomeUnknown`, and retries with the same identity return the original record instead of replaying it. Compacted history keeps request identity, so a late retry is refused (R5).
4. **Muse session MCP relay helper.** The supervisor binary in `--relay-mcp <session>` mode exposes three schema-validated tools, overwrites the owning session from argv and enforces user opt-in, budgets and revocation server-side. See F1 for the token it uses.
5. **Repository and filesystem.** Git runs with hooks and fsmonitor disabled and signing off, bounded output and timeouts. Configured clean/smudge/process filter programs are disabled per operation; matching files fail closed rather than being silently converted or committed as raw bytes (F9 below). File context is Git-visible, repository-relative, symlink-refusing and limited to 64 KiB of non-binary text. Developer test commands run in their own process group or Windows job and are killed with their descendants. State files are created without following links and with private permissions.
6. **Data lifecycle (R5).** Backups use a single-transaction `VACUUM INTO`, are verified (integrity check, schema, required tables, SHA-256) before export, import or restore, and refuse newer schemas. Restore is staged and applied only at the next start under the owner lock, after an automatic backup, with the current account policy reinstated so no restore can switch billing routes.
7. **Image staging (R14).** Bytes enter only through bounded, owner-authenticated chunk operations into a private per-session folder, are typed by content, checked for size, dimensions and SHA-256, and are read by the session worker only on explicit send after a second checksum check. The journal stores IDs, not bytes. The relay helper cannot reach these operations.
8. **Support report (R7).** Built in Rust from an allowlist of counts, states, versions and short identifiers; free text (task and transcript text, paths, names, account identity, keys, error messages, provider output) is never copied, and identifiers that do not match a short machine-token pattern become `other`. Session IDs are replaced by ordinal labels. The user previews the exact text; saving writes that remembered preview (10-minute expiry) through the same private, atomic, outside-state destination checks as exports. Nothing is uploaded. Lascoria keeps no log files; worker stderr is an 8 KiB in-memory tail.
9. **Network.** Muse installation uses a pinned vendor manifest with SHA-256 and size verification over HTTPS. Lascoria does not otherwise open network listeners. Optional BYOK decision providers (R10) are described in [decision assistance](decision-assistance.md): compiled-in endpoints, vault-stored keys, per-mode and per-workspace consent, bounded admission and no automatic retries.

### F1 residual risks

Peer binding stops a script that only reads the token. Status of the ways same-user code could still impersonate an accepted executable:

- **Relay helper argv: closed 19 October** (`supervisor/src/relay_identity.rs`). With binding on, a helper is accepted for a session only when (1) it presents that session's relay capability, a random secret issued for each host generation, given to the worker over its private pipe and to the helper by Muse in its environment, never journalled, reported or written by Lascoria or Muse; (2) it descends from this supervisor through a Muse host (helper, host, SDK worker, supervisor, at most four levels); and (3) its parent is the host that the first accepted helper for that capability came from. Muse starts the helper when the session starts, before any model turn can run a tool, so a tool or script started under another session's host, or outside Lascoria, is refused even with the capability copied from the helper's environment. `test/relay-identity.test.js` (Linux and macOS, real Muse) shows the Muse-started helper working before and after a supervisor restart, and refuses a helper run by a script with no capability, a guessed one and the real one copied from `/proc` or `ps eww`; the capability appears in no Lascoria or Muse data file. Residual: a program that already controls a session's Muse host process can act as that session, which grants nothing beyond that session's own tools. Windows x64 passed the same test natively on 19 October (without the copied-capability case, since Windows offers no same-user environment read).
- **Code injection into the accepted desktop binary: platform-specific resolution.**
  - macOS: signed builds use the hardened runtime, which refuses `DYLD_INSERT_LIBRARIES` and debugger attachment by other programs. Implemented 19 October (`check_desktop_signature` in `supervisor/src/peer.rs`): a release supervisor is built with the Developer ID team (`LASCORIA_APPLE_TEAM_ID`, set by the release workflow from `APPLE_TEAM_ID`) and refuses a desktop peer whose running code does not satisfy `anchor apple generic and certificate leaf[subject.OU] = <team>`, checked by the system against the running process. Unsigned QA and development builds have no team and skip it. A macOS unit test checks the requirement against a running Apple binary; the actual Developer ID-signed runtime peer check passed on 21 October, including same-path ad hoc refusal and restored-signature acceptance. Signed distribution and notarization remain in [public launch](public-launch.md).
  - Linux: implemented 19 October (`process_interference` in `runtime-support/src/platform.rs`). A desktop peer that is being traced (`TracerPid` not 0) or was started with `LD_PRELOAD` or `LD_AUDIT` is refused, and so is one whose process status cannot be read. Unit-tested, and `test/relay-identity.test.js` shows the real client refused when started with a preloaded library. Remaining: injecting into an already running desktop process needs `ptrace` rights that Ubuntu's default Yama setting (`ptrace_scope` 1) does not give a same-user program, unless it started the desktop itself, which the tracer check catches.
  - Windows: no reliable user-mode check exists for a same-user program that injects a DLL or a remote thread into the running desktop. Same-user code there can equally read Muse's own credentials and change the user's repositories, so this is **accepted** as a platform limit of a same-user threat on Windows (Kamba, 19 October).
- **Identity read at connection time.** The executable and process tree are resolved from the peer PID once per connection. PID reuse between connect and lookup is not exploitable without the token and, for helpers, the capability.
- Hashing an unfamiliar executable runs on a blocking thread and is cached for 16 paths, so a hostile peer cannot stall other connections.

## Adversarial local clients (19 October)

`test/ipc-adversarial.test.js` (runs in local CI on macOS and Linux) sends hostile requests straight to the supervisor's socket: not JSON, truncated JSON, invalid UTF-8, no token, a wrong or 60,000-character token, a wrong protocol version, an unknown or non-string operation, 20,000 levels of nested JSON, a line over the 64 KiB frame limit, a start request with an impossible workspace, an empty line, a connection that never sends, and 24 slow connections at once (more than the 16 admission permits). Each is refused or closed; afterwards the same supervisor answers, with no session or journalled command created. Accepted residual: a same-user program can keep the 16 permits busy by reconnecting every five seconds, delaying the app; such a program can equally stop the supervisor, so this adds no capability. Named pipes on Windows need the same run natively.

## Native drops (19 October)

`read_dropped` returns the bytes of one regular file from the most recent native drop, selected by drop token and position; the page cannot name a path, an older drop or a folder, and files over 100 MB are refused. The user chose every path by dropping it. Bytes then pass the same staging checks as chosen files.

## Supply chain (19 October)

`node scripts/check-supply-chain.js` (also `npm run supply-chain`, and a required step of the release workflow's plan job) runs `npm audit` over the whole npm graph, `cargo audit` over the supervisor, desktop and runtime-support lockfiles, and a licence check of the shipped npm packages and every third-party crate. It fails on any known vulnerability, on an advisory warning not reviewed in the script (each reviewed one carries its reason), and on a licence outside the allowed permissive set (MPL-2.0 allowed as file-level copyleft). It needs the npm registry and the RustSec database, so it is a release and dependency-change gate rather than part of offline local CI.

### Native drop boundary review (19 October)

The first drop implementation read as many as sixteen 100 MB files before composer validation, and asynchronous completion could target a newly selected session. Intake now checks eight files/100 MB aggregate before egress from native storage, serializes reads, enforces the remaining allowance on the opened handle and binds delivery to the originating session. Native reads reject non-regular files; Unix opens use O_NONBLOCK so a file replaced by a FIFO cannot occupy a blocking reader indefinitely. Five Node regressions and a Rust allowance/regular-file/FIFO test pass; Windows desktop check and Clippy pass. Native physical drags and Windows special-path validation remain part of the platform gate. This bounds one intake, not total WebView memory or all pending attachments.


## Hostile Git conversion filters (F9, 21 October)

**Medium: confirmed and mitigated for the tested stable-configuration boundary.** A disposable repository configured a clean filter that wrote a synthetic marker. The original snapshot command (`git diff --no-ext-diff --no-textconv --binary HEAD`) returned success and created the marker despite disabled hooks. Read-only inspection was therefore capable of running a repository-configured conversion program.

`supervisor/src/git.rs` now owns background Git process policy for snapshots and workspace operations. It reads effective filter names with null delimiters before each operation, overrides clean/smudge/process commands to empty and marks each driver required, so files selecting those drivers are refused without execution. Unused configured drivers do not block ordinary files. This deliberately does not silently bypass conversions such as Git LFS for staging/commits; the error and Help direct the user to their Git client. Configuration reads are limited to 16 KiB, names to 128 bytes/64 drivers, policy arguments to 8 KiB, stderr to 8 KiB and operation output to 1 MiB, within the existing total 5/8-second deadline. No filter command values are copied into diagnostics or journals.

Task isolation creates an owned branch and a no-checkout worktree, then checks out through the guarded path in the target branch's context. This also observes branch-conditional filter configuration. Refused checkout removes its worktree and owned branch; an existing destination or branch is refused without taking ownership. The regression verifies no marker, no remaining task worktree/branch, unchanged source content, and successful normal Project worktrees. The existing real-Muse coding lifecycle exercises snapshot refusal through the public supervisor API and subsequent successful capture, direct tests, commit and archive.

Limits: this is not a sandbox for Git or a hostile same-user program. Git/configuration/attributes can change between processes, and this does not establish an atomic policy snapshot against a concurrent malicious configuration writer. That race, executable replacement, cross-user tests, repository skills/MCP and the remainder of R12 stay open. Windows compilation is checked separately; native Windows/Linux execution of these new adversarial cases is still required.


### F1 signed macOS runtime proof (21 October)

The local Developer ID QA bundle passes team-signature verification with hardened runtime. The actual release-compiled supervisor passed `testing/macos-signing-smoke.js`: accept a signed native fixture, refuse a same-user interpreter holding the token, refuse the fixture at the same allowed path after ad hoc re-signing, then accept its restored valid signature without a supervisor restart. This tests the OS running-code requirement through the production IPC path, including its path-identity fast path. Both embedded runtime hashes match signed provenance. The signed runtime also completed a controlled real-Muse Echo turn. The subsequent signed native Echo/export and final `cf87233` notarized update checks passed as recorded in the release evidence. Remaining R12 adversarial/platform checks are separate. No general same-user sandbox or broader security clearance is inferred.

### Fresh TLS dependency advisories (21 October)

A fresh online supply-chain review found [RUSTSEC-2026-0382](https://rustsec.org/advisories/RUSTSEC-2026-0382.html) and [RUSTSEC-2026-0383](https://rustsec.org/advisories/RUSTSEC-2026-0383.html), concerning trust in distrusted emSign intermediates. Both the supervisor and desktop lockfiles now resolve `rustls-webpki` 0.103.16 and `webpki-root-certs` 1.0.10, the stable patched versions. Only those package versions/checksums changed; existing compatible dependency choices were preserved. No advisory suppression or TLS verification bypass was added. The new dependencies were fetched separately from local CI.

`node scripts/check-supply-chain.js` passed after the updates: zero npm vulnerabilities, five shipped npm packages and 843 Rust crates checked, with the same five previously reviewed warnings. This is a dated dependency/license audit, not complete R12 security clearance. Final-head offline CI and any distribution rebuilt with these lockfiles must be recorded separately; the final `cf87233` notarized QA versions include this dependency patch. Subsequent source changes, including F10, require fresh distribution builds and acceptance.


## File-manager fallback and executable documents (F10, 21 October)

**Medium, fixed in source; platform release acceptance remains open.** Combined review found that Open in editor with the default system handler sent arbitrary contained files to the OS open action. On Windows, ShellExecute with open launches executable files, so inspecting a repository program could execute it. The code path and [documented OS semantics](https://learn.microsoft.com/en-us/windows/win32/shell/launch) establish the issue; no untrusted executable was run to demonstrate it.

The fallback now accepts directories only, before OS dispatch. Individual files require an explicitly selected editor. Windows uses the explore verb, and macOS uses the OS reveal action so a directory named .app is shown in Finder rather than launched. Settings and Help explain the boundary. Regression checks cover executable/script/shortcut/text files, missing paths, normal folders and the macOS application-bundle command arguments. Path containment and editor selection remain unchanged. Concurrent same-user path replacement is not an atomic filesystem sandbox; the existing R12 residual boundary still applies.

Scoped macOS native validation used the fresh isolated QA build: a session root named Workspace.app was revealed/selected in Finder, and an individual text file was refused with the editor-selection explanation. The follow-up error action opens Editor settings rather than reconnecting a healthy supervisor. Final current-source validation is recorded in PR #1; Windows/Linux native distribution remains open.
