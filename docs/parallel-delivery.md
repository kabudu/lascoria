# v0.5.0 parallel delivery plan

A developer can see which parallel Muse task needs a delivery decision, pass only selected evidence between tasks, notice file overlap, and bring a blocked PR back into the existing review flow. The Rust supervisor owns Git and durable receipts. The official Node SDK worker continues to own Muse. The UI keeps the task card and Attention as entry points.

## Build order and interfaces

1. **Task delivery status.** Extend the bounded GitHub observation with base branch and merge state. Join observations to the recorded task and folder, keep their observed revision visible, and show one cue for waiting on checks, review, checks/feedback failure, base lag or conflicts. Unknown and closed observations cannot masquerade as a healthy open PR. Status actions open the matching task and Workspace folder.
2. **Task handoffs.** Add supervisor-owned directed links between two recorded tasks in distinct local sessions. Store bounded selected evidence with its source identity and revision. The evidence choices are a captured diff excerpt, a recorded test result, or a developer-authored decision. Preview the exact outbound text, verify the source when saving and when copying into the recipient draft, and show stale or unavailable evidence without treating it as current. The destination draft remains editable and sending to Muse is explicit. Retain local links and snapshots through restart; reject self-links, conflicting retries and dependency cycles.
3. **File overlap.** Observe bounded path-only Git status for open managed worktrees. Group by canonical Git common directory and compare distinct session folders. Show both owners and the common path in Workspace, with a quiet cue on the affected task. Compare committed task changes as well as working changes where the base is known. Suppress matches from unrelated repositories, return path names only, and expose incomplete observations if scope or limits prevent a complete scan. Use paced visibility-aware refresh with at most one UI request in flight.
4. **Update from base.** Use a current same-repository GitHub PR and the configured fetch destination. Fetch the observed base without updating branches, preview incoming paths/commits and bind the review to the worktree, heads, source and clean status. Recheck on apply. Merge using Git in the isolated worktree without automatically committing or pushing. Disable configured conversion/merge commands and hooks for this flow. Use the per-session lane and existing command journal. Git's pending-merge metadata is authoritative for recovery, and only a matching Lascoria intent enables its finish or abort controls. Inspect conflict paths, ask Muse through the draft, and either stage resolved paths and explicitly create a reviewed merge commit, or abort the update. If a writable operation times out, refresh and reconcile against Git before retrying. Reject a changed branch, stale review, dirty worktree, foreign Git operation or unsupported repository state. Bind test evidence to current workspace content and head before sending a merged update back to delivery.

## Boundaries and recovery

- **Authority.** Desktop IPC admits project and Git writes to the owning session lane. Other lanes can continue during a merge. GitHub metadata supplies the observed PR head and base; the reviewed object IDs and locally bound destination determine the update. Git writes only the isolated worktree. Merge drivers, Git hooks, automatic stash and overwriting ignored files are disabled for this operation.
- **Evidence.** The supervisor derives the preview body and revision from its own records and files. A handoff accepts an exact repeat of its request identity, refuses a different payload with that identity, and rechecks the source before it can be added to the destination session draft. Saved handoffs are bounded to 64 and purged from working state when either archived endpoint is explicitly removed. Imported or recovered evidence can be inspected but requires a source check before copying.
- **Observation.** File scans return paths and task identities. One scan per service inspects at most 12 worktrees, uses four bounded workers, and caps each worktree at 256 paths and each result at 32 overlaps. A 20-second visible-window refresh keeps scanning off the status hot path. Truncated or unavailable scans are marked incomplete.
- **Conflict recovery.** An applied or interrupted Lascoria merge intent is matched against Git's current branch, HEAD and MERGE_HEAD. The pending review is tied to the worktree contents and index. Staging must select one unmerged path. Commit and abort use confirmation bound to the reviewed state. The merge commit holds Git's index lock during the final review check and uses a private copy of that index. A successful supervised push retires the fresh-check requirement for that merge. Git operations begun elsewhere are left to the user's Git client.

## Validation checklist

- [x] Inspect existing review, Git and relay boundaries and define the four slices.
- [x] Build and test task status, ownership, keyboard entry and stale observations.
- [x] Build and test directed handoffs, exact preview, revision checks, draft-only delivery and restart.
- [x] Build and test path overlap, paired task navigation, unrelated repositories and observation budgets.
- [x] Build and test clean and conflicting PR updates, stale previews, external edits, abort and fresh validation before push.
- [x] Run the integrated three-session scenario through the desktop bridge, real Git and controlled Muse and GitHub endpoints. A hands off to B, B and C overlap, one PR becomes blocked, and the developer resolves or aborts then delivers a checked fix while another session can proceed.
- [x] Review safety, revision checks, resource caps and compatibility, then push the implementation.
- [ ] Run full local CI and hosted checks on the reviewed revision. Record the exact evidence in the PR.

The integrated check must show the task and revision at each entry point, preserve unrelated work and prove observed test/push/PR results. A controlled scenario verifies behaviour and failure boundaries. Comparative developer timing and live subscription acceptance are tracked separately.

The controlled macOS scenario uses actual Muse Code 1.4.25 and the official SDK, real Git worktrees and a bare remote, a controlled GitHub CLI, React and the Rust desktop bridge. It fetched a base commit absent from the task repository without moving its tracking branch, confirmed that an unrelated repository with the same filename produced no overlap, observed CI pending and review-ready states, checked a source change and a rejected cyclic handoff, opened the correct peer worktree, preserved a stale-preview edit, refused conflict markers, aborted cleanly, ran another session while a merge was pending, accepted an explicit one-time Muse tool approval, required a fresh passing check, and verified the pushed Git commit. It also checked the conflict panel at 820 pixels, accessibility, a clean base update without an automatic commit, and handoff retention after restarting the supervisor.

The first full CI run caught a macOS path-alias regression in existing delivery reads. The strict canonical-worktree check now applies to preview and write operations; ordinary reads continue to accept legacy aliases. All seven delivery tests passed after the correction.
