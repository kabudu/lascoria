# Sessions and multi-folder projects

Status: R15 is partially implemented. The initial reusable Project flow saves up to eight named folder references, supports keyboard reordering/default selection and starts native multi-folder Muse sessions. Native Browse selection is implemented alongside editable paths. An edited Project can be applied to an existing session with its next task. Spatial folder cards, drag/drop, optional goals/notes and full platform acceptance remain open.

## Two clear starting points

The Start action offers **Session** and **Project**. A Session is quick: choose a folder, describe the task and start. A Project is a named, reusable workspace: add its folders, give them clear names such as App, API and Shared, choose the default working folder, then describe the work. Do not make quick sessions require project setup.

A project setup can echo the spatial workspace: folder cards surround the project goal and can be arranged without changing their meaning. These are context references, not task dependencies. Also provide an equally capable keyboard/list view; dragging must never be required. A compact summary such as **Project name · 3 folders** opens the folder list when needed. Keep that context detail off the main task canvas by default.

Before starting, show exactly which folders Muse will work with and which is the default. Preview a full path on demand, disambiguate equal basenames and name missing/unavailable folders. Add-folder supports normal folder selection and drag/drop, with reorder/remove, clear validation and no automatic model call. Folder notes and the project goal can explain how the parts fit together. Do not recursively paste every file into the prompt or claim all folder contents are already loaded.

## Native context, not just labels

The pinned official SDK 1.4.10 (same MSP schema fingerprint as 1.4.9) declares `session/start.workspaceRoots`: an ordered set of absolute, canonical, existing directories. Its first root is the native CWD/default folder. Additional roots receive native workspace rules but grant no Project Trust. If the singular `workspaceRoot` is also supplied, it must match the first canonical root.

The SDK also declares `turn/start.workspaceRoots` as a sticky replacement taking effect at that turn's launch. Omission keeps the current roots. Explicit null is invalid, and a root replacement cannot be sent with an immediate steer. These declarations require native/provider verification before shipping; naming folders in Lascoria or adding a text manifest alone does not implement native multi-folder context.

Keep one authoritative, revisioned project configuration with stable project/folder IDs, display aliases, canonical paths, ordered default root and optional notes. Record the exact project revision/root set applied to each session and the native command receipt. A human-readable context summary may complement that native configuration; it must not substitute for it or imply files have been read.

## Editing without surprises

Editing a project changes the reusable setup for future sessions. Show a short change summary and let the user deliberately apply it to the selected existing session at the next task boundary. An active task keeps its current folder context. A pending change is clearly labelled and can be cancelled; never replace roots through an in-flight steer or silently change the selected billing/model route.

Show configured versus applied folder context only when different. A failed, stale or unknown application keeps the prior confirmed context visible and retains the request identity for safe reconciliation. Reopen/resume must recover project identity, aliases and applied revision without rebinding to a different directory. Missing, moved, nested, duplicate, symlinked or offline roots need explicit recovery with no silent folder substitution.

### Next-task folder changes (implemented 17 October)

When the saved Project is newer than the folders a session uses, the composer shows a short summary (added, removed, moved, renamed, new order) and **Use the updated folders for this task**. Nothing changes until the user starts a task with that box ticked. Plain tasks keep the current folders, a running task is never changed, and steering cannot carry folders. Changing the default folder is refused for an existing session, because the default folder is its working directory and the scope of the file browser and Git guards; the offer says it needs a new session.

Protocol: the optional `projectContextUpdates` capability adds `turn.projectRevision`. The supervisor accepts it only for the session's own Project, for a saved revision newer than the applied one and with an unchanged default folder, and only when the session is idle. It revalidates every folder, records `projectContextPending` (revision, request ID, snapshot) durably before dispatch and sends the ordered folders as the official `turn/start.workspaceRoots` sticky replacement. The applied `projectContext` changes only after the journalled turn is confirmed (`projectContextReceipt.appliedWith: "turn"`). A refused turn drops the pending change; an unknown outcome keeps the last confirmed folders visible and the change offered, because re-applying the same folders is idempotent. A lost reply is reconciled from the journal on retry or before the next task, without a second task.

Muse 1.4.10 accepts the replacement (`disposition: "started"`), but in controlled tests it keeps describing the session-start folders to the model: its workspace-identity reminder still lists only the original folders (observed, not documented). So the applying task also carries a short model-visible note naming the new folder set (folder names and absolute paths, default first), sent as a separate input part with `displayText` set to the user's own words. The transcript and task names show what the user typed. A plain task or a shortcut skill cannot carry the note; a folder change with a shortcut is refused and asks for a plain task first.

Evidence (`test/project-context.test.js`, real pinned Muse 1.4.10 with a controlled loopback model): saves never change a running session; already applied, superseded and steering changes are refused; a busy session refuses the change; the applying task reaches the model with the new folders named; the transcript keeps the user's words; a lost reply returns the same command; the applied revision survives a supervisor restart and recovery; and a removed new folder blocks the next task. Rust tests cover scope, staleness, default-folder refusal, the note and journal settlement. The Rust-backed UI test (`test/ui/project-update.spec.ts`) covers the offer, a plain task that keeps the old folders, applying, the default-folder refusal, narrow layout and accessibility.

Not established: what the native replacement changes inside Muse. With the test permission profile, Muse's file tools read and wrote outside the configured folders without approval, so neither read nor write behaviour distinguishes the old and new folder sets, and Muse exposes no read-back of a session's current roots. Native permission behaviour for added folders, with a real permission profile, remains an R15 acceptance item.

## Git, permissions and scale

Keep native permission/trust authority. Adding a folder must not approve tools, grant Project Trust or make a read-only promise the runtime does not enforce. External context notes/repository instructions are untrusted task input.

Define Git ownership per folder/repository. Existing isolated tasks own one worktree; do not imply that one primary worktree isolates edits across every project root. Before enabling isolation/commit/diff for a multi-repository project, implement and validate repository-scoped worktrees, selected repository actions, attribution and cleanup, or explicitly block the unsupported combination. Never stage or discard changes in an unintended sibling repository.

Bound folder counts, context manifests, discovery work and session admission. Preserve existing streaming, recovery, evidence identities and token observability. Define portable path handling and migration for all three operating systems. R15 completion requires real cross-folder implementation and native permission/recovery/Git validation, not just setup screenshots.

## Session and project names

User clarification on 15 October: standalone Session creation offers an optional name, with a useful workspace/task-based default when omitted. Users can rename it afterward from an obvious session action. Project creation asks for a name; the name can be edited afterward. Names persist across reopen/recovery and update consistently in the session list, canvas, attention queue, local communication picker and project context. Renaming changes display identity only, never native session IDs, folder paths, command/delivery IDs or permissions. Define trimming/length limits, duplicate-name disambiguation, empty-name defaults and keyboard/screen-reader behaviour.

Standalone naming now offers **Session name (optional)** at creation and **Rename session** beside the current session heading. Names are trimmed, limited to 100 characters / 400 UTF-8 bytes and reject control characters. Blank names use the primary folder basename. Duplicate names are allowed; session lists, attention, targets and local peers retain short native IDs. Names propagate through the existing status refresh without another model call. Existing presentation labels remain a fallback for older sessions until deliberately renamed; older supervisors retain their original label control.

The optional protocol-v1 `sessionNames` capability accepts `start.name` and owner-authenticated `session/rename` with `sessionId`, `name`, `expectedRevision` and a stable request ID. Status adds `displayName` and `nameRevision`. Rename records are separate from worker state, retained through recovery and archived-session inspection, and do not change native IDs, paths, command IDs or permissions. A lost reply retries the exact compare-and-set; stale concurrent edits require an explicit choice. Reopening the dialog does not silently replace an edit. This implements standalone naming, not the required editable Project entity.

## Initial reusable Project increment

The Start dialog keeps Session as the quick default and adds Project when the supervisor advertises `projects`. Project setup requires a name, one to eight labelled absolute folder paths and an explicit Save. The first folder is the default; Up/Down and Remove are keyboard accessible. Saved projects can be selected, renamed and edited for future starts. Reload saved project explicitly replaces the unsaved setup after a conflict. Browse opens a native directory-only chooser for each folder; editable full paths remain available. Drag/drop and spatial arrangement are still release work.

Owner-authenticated protocol-v1 `project/list` returns at most 100 saved configurations without retained retry payloads. `project/save` accepts a UUID `id`, required `name`, ordered `folders` (`id`, `name`, `path`) and `expectedRevision`, with a stable request ID. Names use the standalone name bounds. Paths are bounded to 4096 bytes and canonicalized; duplicate/nested roots and duplicate folder IDs are rejected. Symlinks resolve before save and the resulting paths are shown. Unknown fields are rejected. Filesystem probes run outside the DB lock on blocking threads, with two concurrent probes and a five-second response timeout; a timed-out OS probe retains its permit until it exits, preventing retry fan-out. The last exact save request reconciles a lost reply without another revision; stale edits retain their input until an explicit reload. Local configuration lives in separate supervisor records, avoiding worker snapshot overwrites.

`start` accepts `projectId` and `projectRevision` instead of a standalone workspace. Admission revalidates the exact saved revision and canonical roots before effects. The worker passes ordered `workspaceRoots` and a matching primary `workspaceRoot` to the official SDK. Session rows retain immutable `projectContext` and `projectContextReceipt` (request/status/command identity); requested folders are not labelled applied until the native start receipt confirms them. Editing the saved Project never mutates this session snapshot. The compact folder disclosure identifies the applied revision, default folder and exact paths. It records the name at application time; later reusable Project renames do not rename existing sessions.

Project starts reject isolated worktrees. The existing file browser/change preview covers only the default folder and says so; combined snapshot capture is disabled in the UI and rejected by Rust. Existing managed-worktree checks still govern commit/discard. These guards preserve the single-folder workflow without claiming repository-scoped Project delivery. Turns and worker recovery revalidate saved session paths and refuse missing/rebound roots. Recovery retains native roots rather than substituting the latest reusable Project configuration.

Validation for this increment uses the actual pinned Muse runtime and official SDK with a controlled loopback model: both roots appear in native model context, remain after supervisor restart, and stay at the original revision after a Project edit. Rust tests cover durable configurations, conflicts, exact retries, nesting/duplicates/unavailable roots and symlink rebinding; the real Rust-bridge UI test covers reorder/default, concurrent edits, lost save/start/task replies, one resulting session/task, narrow layout and accessibility. This is runtime integration evidence, not a live-provider cross-repository coding or full native platform acceptance claim. Next-turn replacement and the complete R15 matrix remain open.


## Initial macOS live acceptance

An isolated native trial with browser subscription login and Muse Wonder completed a real question/answer, read and edited one file in each of two synthetic repositories, left tests unchanged and passed both suites. Closing the UI left the QA supervisor available. After an isolated supervisor restart, the recovered live session ran both suites again with its original roots and primary CWD. Editing the saved Project name/order advanced its revision without changing the existing session snapshot. The native 800px review also checked folder disclosure, Rename access, dropdown sizing and the default-folder Git guards. This establishes an initial macOS workflow, not the complete R15 platform or permission matrix.

Pinned SDK compatibility: Muse 1.4.9 refused a bash tool's direct `workdir` in the secondary root with `workdir escapes workspace`. Native file reads/edits in that root worked, and explicitly changing directory inside the bash command ran its tests. It has not been re-tested on 1.4.10. Treat the first root as the reliable initial shell CWD; do not promise identical direct-workdir support across every native tool. SDK upgrade/parity verification and secondary-root permission/refusal coverage remain part of R15.


## Native folder intake

Session and Project setup offer Browse beside each editable path. The platform chooser selects one directory. Cancel preserves the existing entry, picker failure offers retry/manual entry, and pending selection blocks Save/Start and Project reordering/removal. Choosing does not save, start a session, read file contents, invoke a model or approve Muse tools. Explicit Project Save still canonicalizes and validates roots; Start uses the existing native session boundary. A selected Project path is an unsaved edit until Save succeeds.

The desktop-only `pick_workspace_folder` command uses the pinned official Tauri dialog plugin through Rust, parented to the requesting window. It accepts no renderer-provided path/filter/permission arguments and permits one outstanding chooser per app. The permit remains held until native dismissal even if the requesting WebView disappears. Only an absolute UTF-8 path of at most 4096 bytes without control characters returns; extended Windows paths use ordinary form. The plugin's general open/save/message IPC permissions and filesystem plugin are not enabled. No filesystem grant or protocol/supervisor change is added. Native OS picker acceptance is separate from the Rust-backed UI's controlled chooser responses.
