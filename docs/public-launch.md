# Public launch gates

This tailors the bootstrap-novel-software-project guidelines to the existing Lascoria product and release backlog. It does not create a new project, repeat the naming exercise, replace the approved brand, authorise a merge/publication or require outside assessors. Implementation, verification, planned work and unsupported cases stay separate.

The maintainer owns these gates. Evidence must name the exact revision, tool/runtime versions, target OS/architecture, command and result. An independently reproducible check is sufficient; certification, external audits, participant recruitment and market-fit evidence are optional stronger-claim tracks unless explicitly requested. Technical correctness, privacy, accessibility and the three required platforms remain release requirements.

## Release mechanics and presentation

- [ ] PL12: define immutable software/version/tag ownership, protocol/data-migration compatibility, dependency/runtime provenance, checksums, signing/notarization and updater verification under R2/R3. Test rollback and resume after partial publication. Before retrying an upload, reconcile remote version and checksum; fail on conflicts, ambiguous state or authentication failure. Honour valid Retry-After deadlines within bounded cumulative wait/attempt budgets, without blind paid or artifact retries. The prepared immutable publisher and staged beta-manifest recovery have controlled API-fixture coverage; actual hosted publication remains unexercised while private.
- [ ] PL13: maintain versioned curated release title/body sources separately from CHANGELOG.md. Use a title such as Lascoria vX.Y.Z: short theme; concise opening, material changes, compatibility/support limits, one primary install path and evidence links. Keep each prose paragraph/list item on one source line. Do not duplicate the title, dump the changelog, enumerate assets already rendered by the host or use U+2014.
- [ ] PL14: fail release automation closed when curated metadata is missing or mismatched to the tag. Preview rendered release notes at desktop and narrow widths, inspect wrapping/hierarchy/links and missing assets, then inspect the canonical page after explicitly authorised publication. Correct metadata if rendering differs. Publication remains separate from commit/push or PR review.
- [ ] PL15: use a scoped branch, reviewed PR and final-head local CI; inspect remote diff/reviews/mergeability. Merge, synchronise the default branch and clean up only when authorised and applicable gates pass. The current stacked draft PR is preserved; this checklist does not retroactively authorise merging it or rewriting the stack. The reviewed policy file `.github/master-protection.json` is prepared, not applied; verify the native status-check contexts from a real authorised public run before applying it.

Stop-ship conditions include unresolved data-loss/replay or permission bugs, secret/private-data exposure, unverifiable installer/update integrity, unsupported required platforms, stale or mismatched release evidence, or public claims stronger than the validated behaviour. A missing outside assessor or unproven novelty is not a stop-ship condition for truthful narrower claims.
